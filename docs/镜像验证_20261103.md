## 2. 结论

### 2.1 `starvla-robodojo-client:v4.6`：仿真栈可用

AIDC 上验证到：

- 解释器 `/opt/robodojo-env/bin/python` 与 `/opt/robodojo-proxy-env/bin/python` 都存在，Python `3.11.15`。
- 源码目录 `/workspace/RoboDojo` 存在，`README.md`、`pyproject.toml` 的 SHA-256 已记录。
- `torch==2.7.0+cu128`、`isaacsim==5.1.0.0`、`isaaclab==0.54.3`、`transformers==4.57.6`、`torchvision==0.22.0+cu128`。
- `EGL`、`Vulkan`、`GLX_nvidia` 都可加载，GPU 驱动能力为 `all`，适合作为 RoboDojo 原生仿真基线。
- 该镜像 **没有** `vllm`（探测结果为 `null`），因此不能单独在一个容器里同时跑 Qwen 服务。

这是目前最适合先跑 RoboDojo 原生 episode 的镜像。

### 2.2 `qwen35:m_n`：Qwen 推理栈存在，但不是仿真镜像

北京 debug 上验证到：

- `/opt/eai/qwen/bin/python` 存在，Python `3.11.14`。
- `vllm==0.17.1`、`torch==2.10.0+cu128`、`torchvision==0.25.0+cu128`、`transformers==4.57.6`、`numpy==2.2.6`。
- `/opt/eai/sim` 不存在，`/opt/robodojo` 不存在；该镜像不包含 IsaacSim/RoboDojo 仿真栈。
- GPU 驱动能力为 `compute,utility`，`EGL` 可加载、`Vulkan` 可加载，但 `GLX_nvidia` 不可加载。
- 平台把作业标记为 `Failed`，原因是当前通用预检把 `GLX_nvidia` 也必须为 `loadable`。这只能说明它不含完整图形栈，**不能证明 vLLM/Qwen 服务不可用**。

这像是按 `requirements/qwen35-serving-cu128.txt` 锁定的推理镜像（`vllm 0.17.1 + torch 2.10 + transformers 4.57.6`）。下一步应做的验证是**模型权重挂载后真正启动 `vllm serve`，并做一次工具调用探测**，而不是只看包版本。

### 2.3 `yaoting.huang-test:robodojo-5090-20261030`：仍需用新版清单重探

北京 debug 上验证 GPU 可用，但这个 run 使用的是尚未加入 `/opt/eai/sim`、`/opt/eai/qwen` 候选路径的旧版 `image_inventory.py`，所以只能确认：

- 旧的 `/opt/conda/envs/RoboDojo`、`/opt/robodojo-env`、`/workspace/RoboDojo` 路径都不存在。
- 尚未检查 `/opt/eai/sim`、`/opt/eai/qwen`。

## 3. 对后续接线的影响

第一阶段的拼接方式应为：

- 仿真侧：使用 `starvla-robodojo-client:v4.6`。
- 推理侧：优先确认 `qwen35:m_n` 能否在集群上真正启动模型服务；若可，使用“仿真作业 + `qwen35:m_n` 服务”分离部署。
- 单容器同时含两套栈时，再评估已构建但未发布的 DLP 全量镜像，或把 `qwen35` 镜像作为模型服务独立暴露。

需要避免的错误前提：

- 不要把 `qwen35:m_n` 的平台 `Failed` 视作“qwen 环境不可用”。
- 不要把包能看到 `vllm` 视作“模型一定完成加载与 tool call”。
- 不要把 `starvla-robodojo-client:v4.6` 能拉起解释器视作“episode 已跑通”。
