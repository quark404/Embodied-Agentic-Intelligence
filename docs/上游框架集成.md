# PyRUA-Lean 与 RoboICL 接入说明

**当前主实验已转为 RoboDojo 上的 Qwen/Astra 混合 Agent。**本文件记录早期上游适配器的契约和来源，主评测入口、条件矩阵与原生评分见 [README](../README.md)、[实验协议](../research/benchmarks/mixed_agent_robodojo.md) 和 [`robodojo_native.py`](../embodied_agentic/robodojo_native.py)。早期的 PyRUA/RoboICL 适配器仍可供接口研究，不属于当前主实验条件。

本项目的 [AgenticHarness](../embodied_agentic/harness.py) 管理子任务、工具调用、图像回忆、预算和运行日志；[SubtaskImageMemory](../embodied_agentic/image_memory.py) 在每个子任务开始时保存初始图像，仅允许在同一任务、同一 episode 中回忆。两个上游框架通过 [upstream_adapters.py](../embodied_agentic/upstream_adapters.py) 接入这一共同接口。**目前它们是两条可选择的运行路径，尚未在同一个仿真器中同时运行，也不能直接把两个框架的公开分数当成配对实验结果。**

本轮核对的上游提交：PyRUA-Lean `fdf6e870654254e2c0c891ee407313fa48bdd0f9`，RoboICL `17b379a6deea33f71bd31e05bd60d1daf627acfb`。后续升级上游时需重新检查适配接口。

## 共同调用流程

1. 上游框架先按其原生方法启动仿真器、加载资产并重置任务；每个 episode 创建新的环境和适配器。Harness 不代替上游做安装或启动。
2. 创建适配器，再用 `AgenticHarness(environment=adapter, planner=..., policy=..., memory=SubtaskImageMemory(...), config=...)` 运行。`HarnessConfig.allowed_tools` 必须与适配器开放的工具一致。
3. Harness 从适配器读取当前观察。在子任务开始时保存初始图像；智能体策略后续显式请求回忆时，才把历史图像交给策略。图像保留任务 ID、episode ID、子任务 ID 与相机来源。
4. 每次动作由适配器返回 `StepResult`。**最终成功由上游仿真器或原生评测器判定**；模型说“完成了”不能代替成功判定。运行轨迹和原生评测输出都要保留。

`run_paired` 是适合合成测试的通用多条件运行器；当前 RoboDojo 主实验使用 `schedule.py` 生成冻结任务/条件矩阵，并由 `reporting.py` 配对原生 `_result.json`。`Condition.environment_factory` 仍可供 PyRUA 与 RoboICL 各自的接口实验使用。两种上游适配器的底层动作不同，其成绩不能直接进行因果比较。

## PyRUA-Lean 路径

`PyRUALeanAdapter` 接收**已经启动**的 PyRUA-Lean `ArmToolkit`，要求 `arm="cells"`。Agent 调用的工具是 `python(code=...)`，代码运行在 PyRUA 的 robot API 上；适配器调用 `ArmToolkit.execute_tool("python", args)`，读取 `toolkit.robo.artifact(..., step=-1)` 中的最新相机图像和 robot 状态，交给 Harness。`finish` 不作为成功信号开放给 Agent；适配器只在上游提供实时原生 `episode_done` 时判定成功。仅在评测结束后给分的后端还需要接入最终结果读取，不能把没有 `episode_done` 解读为失败。子任务进度需要另行注入 `subtask_verifier`，不能由 Planner 自己宣称。

LIBERO 可用 `boot_pyrualean_libero(cell, out_dir, ...)` 按 PyRUA 的 `boot → dump_card → LiberoRobot → ArmToolkit(cells)` 路径创建会话。它默认使用 `primitives="no-vla"`，会话结束时关闭 RPent toolkit 和 daemons；仍需在配对实验中为**每个 episode**创建新会话。

实际接入前需确认所选 robot stack 的图像 artifact 名称及相机、可用 Python 原语、每次 cell 的时间/步数预算，以及对应 benchmark 的终止和成功字段。LIBERO-PRO 路径还需按 PyRUA 文档安装 RPent 和机器人栈；RoboDojo 路径使用 XPolicyLab。适配器只覆盖 Harness 与已启动 PyRUA 会话之间的桥接。

## RoboICL 路径

`RoboICLAdapter` 接收**已经初始化并重置**的 RoboDojo 环境。它通过注入的 `observation_reader` 取得新鲜观察，读取左腕、头部、右腕相机图像和公开机器人状态；每次动作后重新读取图像。它还需要注入 `action_converter`、`action_executor` 和原生 `success_reader`：

- RoboICL 的标准模型输出为 `[T,14]` 数值动作块。需要用与所选冻结配置匹配的 `DialogueModel._convert_tensor(rows, state)` 或等价的**已验证转换器**变成环境接受的动作。原始 `[T,14]` 数组**不能**直接传给 `env.take_action`。
- 若采用 RoboICL 的结构化 `mode/left/right/gripper` 动作格式，设 `action_format="structured"`；适配器会延迟调用上游 `validate_actions`。两种格式属于不同实验条件，必须分别标注。
- `action_executor` 应沿用 RoboICL 官方执行路径的动作安全检查、IK 连续性保护和中断机制。适配器记录实际执行步数、丢弃步数及拒绝回执，遇到拒绝时不伪称动作已执行。
- `observation_reader` 应沿用 RoboICL 的相机就绪检查，在初始化和每次动作后提供有效的最新图像。`success_reader` 应读取 RoboDojo 原生任务判定；缺少该回调时，适配器不会自行宣称成功。

RoboICL 自带的示范/轨迹上下文和 LIVE 交互记忆**独立于**本项目的子任务初始图像记忆。若做记忆消融，需要明确开启哪种记忆，避免将 RoboICL 的原生记忆收益误计为本项目图像回忆的收益。RoboICL 所需 Isaac Sim、GPU/Vulkan 栈、固定上游版本和 benchmark 资产仍按其原生配置准备。

## 现有验证与后续需要的环境

`tests/test_upstream_adapters.py` 用伪造的 PyRUA toolkit 和 RoboDojo 环境检查动作桥接、图像读取、原生成功判定及动作拒绝时的回执。另以 PyRUA 当前仓库的真实 `ArmToolkit` 加其自带的假 LIBERO backend、RoboICL 当前仓库的真实 `validate_actions` 加假 RoboDojo 环境做了本地契约检查，均能完成一轮动作；这仍**不是**真实仿真运行。`tests/test_agentic_harness.py` 检查子任务初始图像、按 episode 隔离的回忆、重规划、预算和配对运行器。尚未验证 Qwen 的具身能力，也未将两个上游项目的官方评测主循环合并成同一个实时仿真会话。

后续开展真实实验时，需要提供：

1. 可运行的 Linux GPU 仿真环境、对应 benchmark 的资产和上游项目固定版本；先选一个 benchmark，例如 LIBERO-PRO，或提供 RoboDojo 的完整栈。
2. 每个 episode 的已初始化环境创建方式、相机观察与图像 artifact 名称、允许的底层动作、安全边界、原生成功判定和子任务进度判定。
3. 若使用 RoboICL，提供与动作空间匹配的转换器、带安全保护的执行函数和相机就绪读取函数。
4. 可访问的开源 Qwen 多模态模型服务及具体 checkpoint、推理配置和资源预算；用于配对实验的任务/种子清单。

接入后先做单个 episode 的原生环境验证，再按当前 Qwen/Astra 条件矩阵跑相同任务/种子，并核对日志与原生评测器结果一致。
