# 项目任务规划：具身能力边界与记忆增强

## 一句话目标

让同一个开源模型做同一批机器人任务，逐步给它增加工具、规划和记忆，弄清楚：**模型独自能做到哪里，哪些帮助真正有效，在哪些情况下仍然会失败。**

这里的“具身任务”是让智能体观察场景并操作环境，例如找到物体、抓取、放置，或者在失败后调整动作。最终成绩以仿真器的真实任务判定为准，不能只看模型说“我完成了”。

## 我们想回答的三个问题

1. **能力边界在哪里？** 通用视觉语言模型直接给动作，遇到新物体、新布局、连续多步任务或操作失败时，成功率如何变化？失败主要发生在看错、计划错、动作调用错，还是没有根据反馈纠错？
2. **工具和规划帮了多少？** 给同一个模型查询、机器人原语和分步规划能力后，是否比直接给动作更容易完成任务？代价是多少次调用、多少时间和多少计算资源？
3. **记忆帮了多少，何时反而有害？** 一个长任务包含多个子任务。当智能体回到先前的子任务时，取回当时保存的初始图像，能否更准确地恢复上下文、继续规划并纠错？取回过时图像时，能否与当前观察核对？

我们**不预设**工具或记忆一定提升成绩。实验应同时记录它们的收益、成本和失败案例。

## 对应最初目标的两条研究主线

**主线一：能力上限与泛化边界。** 用 Agent Harness 统一接入模型、仿真环境和动作接口。让通用 VLM 在不使用历史经验的情况下直接操作，再加入工具调用和长程规划，比较“模型本身”和“Agentic 系统”的差距。任务按所需步数、未见物体、未见场景、指令改写和执行扰动分组；逐组看成功率何时明显下降，并从完整轨迹定位感知、推理、规划、工具使用和动作执行的瓶颈。“能力上限”只表示**指定模型、任务集和预算下测得的上界**，不宣称所有具身任务的绝对上限。

**主线二：Planner–Tool–Memory 协同。** Planner 根据目标和当前观察切分子任务；每个子任务**开始时**，Memory Bank 保存对应的初始图像及任务 ID、episode ID、子任务 ID 和目标。Tool 执行查询或机器人动作并返回回执。当智能体后续需要回忆某个子任务时，显式调用检索工具，按子任务 ID 取回**同一任务、同一 episode 内**的相关初始图像，再与当前观察一起判断下一步。每步都检查真实回执并更新状态；失败时重新规划、必要时回忆。这里的 RAG 指**任务级图像回忆**，不构建图像或文本向量索引，也不以相似度向量检索为目标。

## 希望最后能说明什么

- 给出一张可复现的能力图谱：简单任务、长程任务、场景变化和意外失败下，各方案的成功率与常见失败原因。
- 用公平的对照实验说明，成绩变化究竟来自模型本身、工具、显式规划还是检索记忆，而不是换了模型、任务或预算。
- 找到值得继续优化的瓶颈。例如，若多数失败来自“抓取后没有核实结果”，下一步应改进反馈与纠错；若主要是找不到正确历史经验，则应改进检索。
- 产出可复用的评测代码、任务清单、运行记录和失败案例，使后续更换 Qwen 模型或 benchmark 时仍可比较。

这些是**预期研究产出，不是已经得到的结论**。

## 实验如何设计

首轮尽量只换一个因素。选定同一个开源模型、同一组任务与随机种子，保证看到的观察、可用的底层机器人动作，以及动作次数和时间上限一致。

Harness 需要统一记录 `观察 → 决策/子目标 → 工具或动作 → 环境回执 → 新观察`，并设置模型调用、动作、时间和上下文长度上限。比较不同方案时，同时报告成功率和实际消耗；工具或记忆即使提高成功率，也要说明额外成本。图像、状态和允许使用的机器人原语应按实验条件明示，避免某组无意获得额外信息。

| 方案 | 模型得到的帮助 | 要检验的问题 |
| --- | --- | --- |
| A：直接操作 | 当前观察；模型直接决定下一步动作 | 原始能力边界 |
| B：工具调用 | A + 明确的查询与动作工具、执行回执 | 工具是否改善观察与执行 |
| C：规划 + 工具 | B + 子目标与执行后检查 | 长任务是否更稳，失败后能否纠错 |
| D：规划 + 工具 + 图像记忆 | C + 子任务开始时存图像，稍后按任务线索显式回忆 | 是否改善长期状态保持、重访任务和纠错 |

之后再做两种关键对照：只保留最近交互、不提供子任务初始图像；以及提供旧图像、错误任务 ID 或已变化的场景，看智能体会不会盲从。闭源模型如需使用，仅作为单独标注的工具或参考组，不承担项目的主要实验结论。

**图像记忆的调用规则：** 进入新子任务时存一次初始图像，之后的动作结果不能悄悄覆盖它；回忆操作由智能体策略显式发起，指定已出现的子任务 ID。查询必须带任务 ID 和 episode ID，不能把不同随机种子运行中的同名子任务混在一起。返回图像及其任务来源，并标明这是**子任务开始时**的历史图像，不能假装旧图像是当前实时观察。检索失败要明确返回“没有匹配记录”。所有存储与检索事件进入轨迹日志，便于区分“未保存”“没找到”“找到了但没用好”和“记忆已过时”。

**防止“提前看答案”：** 当前记忆只供同一任务、同一 episode 内回忆已经开始的子任务，不能读到其他 episode、未来场景或仿真器隐藏状态。这一版还没有跨 episode 的经验复用；若之后加入共享经验库，只能包含训练任务，测试结果不能回写供同一轮测试使用。测试需同时覆盖不同随机种子、物体或布局。

## 先在哪些 benchmark 上做

近期公开基线、Qwen 的非零成功率证据及其限制见[benchmark 调研](../research/benchmarks/README.md)。选首站时先核查**同一种模型和动作接口**下是否已有可复现的非零基线，再做本项目的真实先导运行；公开分数不能代替本项目结果。

1. **LIBERO-PRO：第一站。** 从一小组桌面操作任务开始，比较 A–D 四组。PyRUA-Lean 已提供相关适配路径，适合先把模型、机器人接口、日志和统计流程跑通。建议固定任务清单，每组使用相同的 20–50 个任务与种子组合；这个数量是试运行目标，不是最终统计保证。
2. **RoboDojo-Sim：第二站。** PyRUA-Lean 和 RoboICL 都涉及该基准，适合检查双臂操作、工具编排、示范与交互记忆。其仿真依赖和 GPU 要求更高，等第一站稳定后再做。
3. **RoboTwin 2.0 / RoboCasa365：扩展。** 前者看双臂和场景迁移，后者看更长的复合任务和状态保持。前两站的对照流程可靠后再扩展。

不能直接拿不同论文的公开总分当作本项目的 A–D 对照；模型、动作接口、任务集合和预算可能不同。

## 分阶段任务与验收

| 阶段 | 要做的事 | 完成时应拿得出的证据 |
| --- | --- | --- |
| 0：评测骨架（已完成） | 统一任务/策略接口、动作回执、训练记忆隔离、简单纠错与日志；用合成任务做接口测试 | 测试能复现；明确标注它不是机器人或 VLM 成绩 |
| 1：首个真实任务 | 接入 LIBERO-PRO 原生环境与成功判定；记录任务、种子、观察、动作、回执、模型版本和预算 | 至少一个开源模型实际完成完整评测流程；失败任务也有可读轨迹 |
| 2：能力边界 | 在固定任务集上运行 A、B、C；按任务长度、未见物体/场景和执行扰动分组；标记感知、规划、工具和动作失败 | 通用 VLM 与 Agentic 方案的配对结果、泛化下降曲线、资源消耗及可复查的瓶颈案例 |
| 3：图像记忆实验 | 每个子任务开始时保存初始图像；支持在同一 episode 按已出现的子任务回忆；运行 D、最近历史、无图像记忆及过时图像对照 | 可追查子任务开始事件、检索目标与返回图像；不读取其他 episode 或未来任务；量出长期状态保持、重访任务和错误后恢复的收益或损害 |
| 4：复核与扩展 | 增加种子和任务；给配对结果计算不确定区间；再迁移到 RoboDojo | 可复现的配置与原始记录；不同基准的结论分开报告 |

主要指标是**任务成功率**；同时记录部分进度、失败后的恢复率、动作/工具调用次数、延迟和模型计算成本。先保留每个任务的原始结果，再汇总平均值；样本太少时只报告探索性发现，不宣称普遍提升。

## 当前状态与下一步

现有合成环境与确定性策略用于检查实验流程，不代表 Qwen 或其他模型的具身能力。本轮初版 Harness 的代码验收重点如下，功能以实际通过的测试为准：

| 规划要求 | 代码层面的验证 | 当前状态 |
| --- | --- | --- |
| 每个子任务开始存初始图像 | 构造两个子任务，核对各自第一帧的原始字节；重访不能覆盖初始帧，存储损坏可由 SHA-256 发现 | 已有合成测试 |
| 需要回忆时才检索 | 显式回忆指定子任务；核对返回图像与“历史图像”标签；不存在的 ID 返回空结果 | 已有合成测试；真实 VLM 尚未验证 |
| 多轮状态与动态纠错 | 模拟失败回执，检查重新规划收到失败原因并能继续；完成结果必须由环境给出 | 已有合成测试；真实扰动尚未验证 |
| 公平对照与能力边界 | `run_paired` 让各方案使用同一任务/随机种子列表和数值预算，记录每组状态；真实实验还需控制模型、观察和机器人动作 | 配对调度已有合成测试；A/B/C/D 真实对照未运行 |
| 防止信息泄漏 | 隔离不同任务和 episode；重复 episode ID 报错；同名子任务的不同运行不能互相取图 | 已有合成测试；跨 episode 经验复用尚未实现 |

目前这些代码检查使用确定性的合成场景；完整的仿真器行为与真实 VLM 成绩，仍需在提供 GPU 仿真环境后验证。下一步将原生观察和成功判定接到统一接口，并接入具体 Qwen 模型执行配对实验。

技术接口和依赖顺序见 [英文研究计划](research_plan.md)。
PyRUA-Lean 与 RoboICL 如何接到共同 Harness，以及各自仍需保留的原生执行与评分流程，见[上游框架集成说明](上游框架集成.md)。
